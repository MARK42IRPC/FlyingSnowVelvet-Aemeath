# 游戏包格式

本文档定义飞行雪绒当前小游戏包的安装格式、目录约束和运行时行为。

## 目标

- 让外部开发者可以交付一个结构正确的 `zip`，主程序即可安装。
- 让游戏代码、资源、粒子、特效与桌宠主工程隔离。
- 让卸载、导出、升级都围绕同一套包目录工作。

## 运行时目录

小游戏安装到共享根目录，而不是项目源码树。

```text
C:\AemeathDeskPet\
  games\
    inbox\        # 待扫描 ZIP
    archive\      # 已安装 ZIP 归档
    rejected\     # 安装失败 ZIP
    installed\    # 已安装游戏
    data\         # 每个游戏自己的存档
    cache\        # 安装和运行缓存
  config\
    games\
      registry.json
```

如果设置了环境变量 `AEMEATH_DESK_PET_HOME`，则以上路径全部改为该目录下。

主程序发布包会额外携带一个内置官方包目录：

```text
gamepack/
  official/
    lahai_tetris.zip
```

运行时会优先扫描这里的官方 `zip` 并自动安装；源码开发环境下如果这个目录不存在，再回退到仓库内的官方样板目录。

## ZIP 根结构

游戏 `zip` 解压后根目录必须直接包含 `manifest.json`。

```text
manifest.json
code/
assets/
extensions/
README.txt
```

允许额外文件，但安装器只认以上核心布局。

## 目录说明

### `manifest.json`

描述包自身、入口类、窗口参数和扩展模块声明。

### `code/`

游戏运行时代码。

- 入口模块必须位于这里。
- 游戏代码应该尽量只依赖宿主提供的公共 API。
- 不要在包代码里写死项目源码根目录。

### `assets/`

包内资源。

推荐子目录：

```text
assets/
  avatars/
  images/
  sounds/
  fonts/
  text/
```

游戏应通过运行时传入的 `GameContext.assets_root` 或 `GameContext.asset_path(...)` 读取资源。

### `extensions/`

游戏私有粒子/特效模块。

```text
extensions/
  particles/
  effects/
```

这些模块不会被复制到 `lib/script/practical` 或 `lib/script/effects`。安装后仍然留在游戏自己的安装目录，由运行时按 manifest 注册。

### `README.txt`

可选，写给安装者或开发者的说明。

## manifest 字段

当前版本要求如下：

```json
{
  "package_type": "game",
  "package_format_version": 1,
  "runtime_api_version": 1,
  "game_id": "lahai_tetris",
  "name": "拉海洛方块",
  "version": "1.0.0",
  "summary": "圆角彩虹字母俄罗斯方块",
  "description": "官方示例包",
  "official": true,
  "author": "Flying Snow Velvet",
  "command_aliases": ["拉海洛方块"],
  "entry_module": "lahai_tetris_pkg.entry",
  "entry_class": "LahaiTetrisGame",
  "bgm_keyword": "星际穿跃",
  "bgm_artist": "鸣潮先约电台",
  "window": {
    "default_width": 1000,
    "default_height": 800,
    "minimum_width": 600,
    "minimum_height": 480,
    "aspect_width": 10,
    "aspect_height": 8
  },
  "extensions": {
    "particles": [
      {
        "module": "extensions/particles/example_particle.py",
        "class_name": "ExampleParticleScript",
        "local_id": "example"
      }
    ],
    "effects": [
      {
        "module": "extensions/effects/example_effect.py",
        "class_name": "ExampleEffectScript",
        "local_id": "flash"
      }
    ]
  }
}
```

## 字段约束

- `package_type` 目前固定为 `game`
- `package_format_version` 当前固定为 `1`
- `runtime_api_version` 当前固定为 `1`
- `game_id` 只允许小写字母、数字、下划线、点、短横线
- `entry_module` 必须指向 `code/` 下可导入模块
- `entry_class` 必须是该模块中的入口类

## 入口类约束

入口类当前约定：

```python
class ExampleGame:
    def __init__(self, context: GameContext) -> None:
        ...

    def create_widget(self, parent=None):
        ...
```

其中：

- `context.install_dir`: 当前游戏安装目录
- `context.code_root`: `code/`
- `context.assets_root`: `assets/`
- `context.data_root`: 该游戏存档目录
- `context.cache_root`: 该游戏缓存目录

游戏控件可选实现 `set_bgm_callback(callback)`。宿主在窗口激活后传入
`callback(keyword: str, artist: str = "", *, track_ref: str = "")`，控件绑定时立即报告当前界面的歌曲，后续只在目标歌曲变化时报告。
传入 `None` 时必须解除绑定；宿主关闭、替换游戏或清理时也会解绑，并使旧回调失效。
回调使用桌宠共享音乐服务与队列，不需要游戏导入播放后端。没有该方法的旧控件继续使用
manifest 的 `bgm_keyword` / `bgm_artist`，包格式版本不变。

可选 `track_ref` 使用音乐服务已有的歌曲引用（如 `netease:3442263555`），提供时直接入队而不搜索，
未提供时按歌名和作者搜索；原有只传两个参数的控件保持兼容。

动态歌曲请求采用独占单项队列：目标歌曲变化时先清空共享队列，再仅加入当前 BGM，以共享播放器现有循环模式循环该曲；
同一目标不重复清空或重播。旧 manifest 静态 BGM 继续使用原有非抢播策略。
退出只暂停仍由游戏控制的当前歌曲，保留此单项队列与进度；迟到的搜索、排队入队/播放与下载结果不能在退出后自动开始。

## 粒子 / 特效扩展规则

这是当前包格式和旧桌宠结构最大的区别。

### 复用宿主既有反馈

需要已有粒子或图片效果时，先复用宿主注册表原名（如 `floating_text`、`burst_line`、
`star_streak`、`smooth_image_show`），不用复制脚本到游戏包，也不用声明同名扩展。
需要窗口内裁剪及独立暂停、关闭生命周期时，使用 `lib/core/services/feedback_scene.py`
的 `FeedbackScene`，在组合边界注入既有粒子/特效管理器，消费共享创建、更新、插值和
`build_particle_batch` / `build_effect_batch`；游戏只提供局部坐标、素材和反馈参数。
场内请求不再发布到全局覆盖层，因此窗口移动、缩放或处于负坐标显示器时不会把坐标混用。

桌面覆盖层仍消费 `PARTICLE_REQUEST` / `EFFECT_REQUEST` 的全局坐标，原事件格式不变。
局部场景由游戏拥有：暂停/隐藏停止推进，重置/续局/关闭清理自己的实例，不清空桌宠全局覆盖层。
静图和 GIF 使用共享 `smooth_image_show`；GIF 动画取帧是宿主图片效果的能力，游戏无需再建播放器。

`FeedbackScene(*, particle_manager=None, effect_manager=None, resource_loader=load_effect_resource, tick_seconds=0.05)`
不订阅桌面事件，不创建窗口或定时器。主要接口：

- `spawn_particle(id, area_type, area_data, options=None)` / `spawn_effect(id, anchor_type, anchor_data, options=None, resource=None)` 返回既有脚本创建的实例；图片可通过仅限进程内的 `resource` 参数提供已解码 `ImageResource`。
- `advance(seconds)` 按 20Hz tick 更新并插值；调用方仅在自身视图活动且未暂停时推进。
- `batch()` 返回共享 presenter 的 `DrawBatch`；调用方负责画布变换、裁剪与绘制顺序。
- `remove(instance)` 撤销单个实例，`clear()` 清理本场景；`particles` / `effects` 是只读 tuple 快照。

`smooth_image_show` 原有静图参数与默认行为保持不变；可选 `animate`（默认假）、
`playback_rate`（默认 1.0）、`animation_loop`（默认真）按资源逐帧时长取样 GIF。
可选 `hover_amplitude` / `pulse_scale` / `intro_scale` 由共享图片效果处理悬浮、呼吸与出生缩放，
默认均不改变原画面。`animation_seconds` 可在宿主对象上提供独立的呈现取帧时钟。

游戏音效复用 `gemes/MAIN/game_sfx.py::GameSfx` 的现有 cue，通过 `play(key, volume_gain=...)`
请求。`cache_dir` 与 `emit` 可在组合边界注入，默认构造与旧 `play_*` 调用继续有效；
发布到声音核心的字段为 `audio_type`、`source`、`volume_gain`、`interruptible`。
包内只保留语义 cue 映射，播放器、WAV 缓存与波形实现继续归宿主所有。

### 1. 扩展模块留在包内

不要把自定义粒子、特效源码塞进主项目全局目录。

### 2. manifest 负责声明

安装器和运行时只根据 `manifest.extensions` 加载扩展。

### 3. 运行时统一加前缀

每个游戏扩展都会注册成：

```text
<game_id>.<local_id>
```

例如：

- `lahai_tetris.glow_burst`
- `lahai_tetris.preview_rise`
- `lahai_tetris.line_flash`

这样做有三个目的：

- 避免不同游戏撞粒子名
- 卸载时可按游戏前缀回收
- 不污染桌宠原有全局粒子/特效 ID

### 4. 包内扩展不要直接用全局装饰器注册

不推荐这样写：

```python
@register_particle("foo")
class FooParticleScript(...):
    ...
```

原因是这会污染全局 ID。

推荐做法：

- 类本身只实现脚本逻辑
- 由 `manifest.json` 指定模块路径、类名、`local_id`
- 宿主运行时用 `<game_id>.<local_id>` 完成最终注册

### 5. 游戏代码应通过 `GameContext` 取前缀 ID

例如：

```python
particle_id = context.qualify_particle_id("glow_burst")
effect_id = context.qualify_effect_id("flash")
```

## 安装流程

1. 对于随主程序发布的官方包，运行时会先扫描 `gamepack/official/*.zip` 并自动安装
2. 对于开发者或玩家手动提供的包，用户可通过游戏管理器选择 ZIP，或将 ZIP 放进 `games/inbox`
3. 安装器解压 ZIP
4. 校验 `manifest.json`
5. 校验入口模块和扩展模块路径
6. 安装到：

```text
games/installed/<game_id>/<version>/
```

7. 刷新 `config/games/registry.json`
8. 动态注册该游戏的粒子和特效扩展

## 卸载流程

1. 关闭正在运行的该游戏窗口
2. 注销该游戏注册过的粒子/特效 ID
3. 删除 `games/installed/<game_id>/`
4. 从 `registry.json` 移除条目
5. 保留 `games/data/<game_id>/` 存档目录

## 导出流程

已安装游戏可以再次打包导出，导出内容就是安装目录自身的标准结构。

也就是说：

- 一个解压态包
- 导出成 zip
- 再重新安装

这三者是同一套 contract。

## 扩展加载的故障隔离

动态注册扩展时，单个扩展加载失败只放弃该扩展，不影响其余扩展、游戏包服务和桌宠启动。失败会记录 `[GamePackages] 跳过粒子扩展 ...` 或 `跳过特效扩展 ...` 警告，包含扩展 ID、模块路径和原始异常。

这条规则是运行时的硬保证，不是容错优化：`GamePackageService.__init__` 先 `refresh()` 再 `bootstrap_official_packages()`，所以一个过期的安装副本必然会在被自动重装覆盖之前先加载一次。若此时异常逃逸，它会穿 `ApplicationState._on_init_ready`，让该回调之后的托盘图标、托盘菜单、音响搜索 UI 和 `APP_MAIN` 之后的全部步骤都不执行——表现为“功能集体消失”，而不是“某个游戏坏了”。

这是双层保护：扩展加载这一层负责隔离单个扩展，ApplicationState._on_init_ready 的阶段隔离负责即使异常漏过第一层、也不会连带吞掉托盘图标、托盘菜单和主界面。任意一层被绕过都不应再复现「功能集体消失」。

因此扩展代码不得依赖“导入失败会立刻暴露”这一假设来自检；请在扩展内部完成自己的校验，并让缺失依赖表现为该扩展被跳过。

## 依赖兼容性

扩展和入口模块可以 import 主程序模块，但对外可见的模块路径属于兼容契约：

- 主程序移动或重命名既有模块路径时，必须同步已安装的游戏包，或通过官方源重新安装覆盖；
- 已安装副本与官方源签名不一致时，`bootstrap_official_packages()` 会用官方源重装，因此官方包只要随主程序一起更新即可自愈；
- 手工安装的包不会自动修复，模块路径变更时需要在 manifest 中升级 `runtime_api_version` 或在包内做兼容处理。
